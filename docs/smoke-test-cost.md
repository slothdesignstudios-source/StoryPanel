# Smoke-test cost: what one 3-panel strip can cost, and what limits it

Scope: `scripts/live-smoke.py run` — one 3-panel strip (prompt in the script), cast and script approval,
reference-conditioned panels with safety and identity QA, one instruction edit, PDF + PNG + CBZ exports.
Traced from the code at this commit; every number below is regenerated by
`scripts/live-env.sh services/backend/.venv/bin/python scripts/live-smoke.py estimate --markdown`.

**A strict USD 5 ceiling cannot be guaranteed.** The application refuses to *reserve* past the cap you
approve, but three things can be billed beyond what it reserved (section 4). The estimate is an estimate,
not a guaranteed upper bound.

## 1. Four different numbers

| Kind | What it is | Value |
|---|---|---|
| **Estimated cost** | Expected provider charges for a clean run, from live prices, measured prompt sizes and *assumed* output sizes | **≈ USD 1.14** |
| **Application admission limit** | The `--approve-usd` amount, stored as a lifetime `SpendCap` on the smoke user. Before every paid call the app reserves that call's maximum in one serialised transaction and refuses (`spend_limit_reached`) if counted + reservation would exceed the cap. The per-project ceiling (`SP_SPEND_LIMIT_PROJECT_USD`, default 8) also applies. A clean run needs a cap of at least **USD 2.21**; if retries need more, the run stops instead | your approved amount |
| **Provider-enforced spending limit** | Only what you configure at the provider. Anthropic documents organisation and workspace **monthly spend limits** you can set (Console → Settings → Spend limits; requests then return HTTP 400). fal: an account is locked when its credit balance falls below a lock threshold *(search summary only, unverified)*. Voyage: none found. I configured none of these, and none is documented to stop a request already in flight | none configured |
| **Charges after timeout or cancellation** | Work the provider may still finish and bill after the app gave up | see section 4 |

- **Estimated cost of a clean run: USD 1.14** (assumed output sizes)
- Counted by the app at the end of a clean run: USD 1.61 (ESRGAN stays at its full reservation until a provider charge is imported)
- **Smallest cap with which a clean run can finish: USD 2.21** (counted total + USD 0.61 for reservations open at the same time)
- Reservations if every bounded retry, QA round and activity attempt were used: USD 20.80 (the approved cap stops the run long before this)

Notes on the table:
- *Reservation / call* is what the app holds before sending. Text: input bound (UTF-8 bytes of system
  prompt + user text + image labels + output schema, + 4,000 tokens for API-added framing) plus the
  full **16,000-token output cap**, which Anthropic documents as a hard cap on output, thinking
  included. Vision images are reserved at the documented per-image maximum of 4,784 tokens.
  After each call the reservation is replaced by usage × price.
- *Expected* uses assumed output sizes (story 5–7K tokens, checks 250–900) and 1K images
  (1,369 tokens each); ESRGAN is assumed to run 10 s. These are assumptions until the smoke test
  measures them.
- Inputs are measured from the simulated run's real prompt templates. Live story text (bible,
  script) will be longer: an extra 20,000 input tokens on every story call adds about USD 0.04 per call.
- Not in the table because the smoke test cannot trigger them: user-edited script moderation (no
  script edit), dialogue re-moderation before export (no balloon edit), character revisions, fal
  fallback models and mask inpainting (not configured), and the server-side text refusal fallback
  (switched off for this run, below).

## 3. Constraints applied for this run (models and scope unchanged)

| Change | Why | Where |
|---|---|---|
| `SP_TEXT_REFUSAL_FALLBACK=false` | With it on, a refused Sonnet 5.5 call can be billed *and* re-run on `claude-sonnet-5` (official refusal-billing rules); the reservation holds only one call. A refusal now ends the run | `config/live-smoke.env` |
| `SP_MAX_CHARACTERS=2` | The prompt names two characters; caps reference sheets at 2 | `config/live-smoke.env` |
| fal `enable_web_search=false`, `thinking_level="minimal"` | Removes per-request add-ons (web search +$0.015, thinking +$0.002 per fal's page summary) instead of relying on defaults. Whether "minimal" itself carries the thinking add-on is not documented in what I could read | `fal_profiles.py` (all environments) |
| Compute-second requests cancelled at their reserved time | ESRGAN reserves 150 s × $0.00111. Before, activity retries could keep waiting on the same job for up to the 40-minute window; now the request is cancelled at 150 s, never resubmitted, and stays an unresolved potential charge. Reconciliation does the same for abandoned jobs | `metering.py` (all environments) |
| Text reservations from bytes + schema + documented image formula | The old `chars/3` heuristic could under-reserve non-ASCII text and small images | `pricing.py`, `metering.py` |
| Panel count enforced before panel images are paid for | A script without exactly 3 panels stops the run at the script gate | brief/script validation, `live-smoke.py` |

## 4. What can be billed beyond the cap

1. **ESRGAN after cancellation.** fal's queue docs (search summary) say cancelling a *running* request
   only signals the runner, which may finish; whether that time is billed is not documented. At most
   3 such jobs (one per final panel). Each is counted at its 150 s reservation; time beyond that is not
   bounded by anything I could verify.
2. **Price-table error.** fal and Voyage prices are **unverified** (search summaries of the official
   pages; the pages are blocked from this sandbox). If a price is wrong, every reservation and estimate
   for that model is wrong by the same factor. Anthropic prices were read from the official page.
3. **Hidden input overhead.** Text reservations assume API-added input is at most 4,000 tokens per
   call. If it is larger, the overshoot is that excess × $2/MTok (Sonnet) or $0.10/MTok (Haiku), e.g.
   USD 0.02 per Sonnet call for 10,000 extra tokens. Output cannot overshoot (hard cap).

Covered inside the cap (counted at their reservation until resolved): Anthropic calls that time out
client-side but complete server-side; fal per-image jobs that finish after a client timeout or cancel
(one fixed price per submission); jobs whose outcome is unknown or lost; failed jobs (counted as billed
by policy). Reservations are serialised, so concurrency cannot overshoot.

**For a strict ceiling** set the provider-side limits yourself: an Anthropic workspace spend limit for
the key used, and a small prepaid fal balance (fal's lock threshold behaviour is unverified). Neither
stops a request already running.
